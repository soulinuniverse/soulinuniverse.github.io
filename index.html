How it runs

            
Spec first,
then code

          

          

            A written spec is cheaper than a rewrite. Every build starts as a document
            you can argue with before a single line is committed.
          

        

        

          
01
Define the problem in writing
Who it is for, what breaks today, what "done" measurably means.

          
02
Spec the system
Data model, screens, edge cases and the things deliberately left out of v1.

          
03
Build the thin slice
One real end-to-end path in production early, so assumptions fail cheap.

          
04
Harden and hand over
Tests, monitoring, docs, access. You own the accounts, the code and the data.
